# 多宿主、多输入方式与语言选型提案

状态：Draft。日期：2026-11-03。本文是待讨论提案，不是接口规格或技术裁定。

后续裁定见 [DECISIONS_2026-11-03](DECISIONS_2026-11-03.md)。下文保留首轮提案原文；已获同意的方向以裁定为准，职责澄清见第 8 节。

## 先说结论

建议把 Scratchmark 定位为可嵌入的笔迹与页面批注能力，同时考虑阅读批注和独立手写板两类使用过程。Windows 与 Android 同等优先；所有列出的输入设备都需要可用的操作路径，但舒适度应按任务验证，不能用“能画线”代替。

语言建议：Rust 作为可移植计算与编辑核心的优先候选，Windows 用 C#、Android 用 Kotlin 承接原生输入与界面；原生手写路径同时作为对照。是否共享实现尚未裁定，尤其不能自动覆盖 PezMax-One 已定的“不共享实现”原则。

## 2 - 产品能力与接入对象

| 使用过程 | Scratchmark 建议负责 | 宿主建议负责 |
| --- | --- | --- |
| PezMax-One 阅读课本 / 试卷并批注 | 笔迹、标记对象的编辑与页面定位、命令历史、可恢复的数据 | 文档打开与渲染、账户、页面身份、文件权限、实际存储与同步 |
| 后续独立手写板应用 | 画布上的笔迹与编辑能力 | 文档 / 页管理、工具栏、模板、窗口及应用生命周期 |
| 其他个人或协作项目 | 同一能力边界与可选择的工具集 | 各自业务、界面、授权与发布方式 |

独立手写板的有限页面 / 无限画布、是否作为 Ether 应用、是否覆盖移动端均未确认。本轮只预留边界，不承诺实现无限画布或多人实时协作。

建议首个验证闭环：打开固定页面 → 书写 / 标记 → 修改 / 撤销 → 保存 → 关闭 → 重开后继续编辑。独立画布也通过该过程验证，不依赖 PezMax 的业务服务。

## 3 - 输入体验建议

以下均为待验证策略。压力、悬停、按钮等按实际能力启用，不按设备名称推断；手指和无真实压感的指针默认固定线宽。

| 输入 | 优先满足的任务 | 建议操作与需要验证的问题 |
| --- | --- | --- |
| 鼠标 | 勾画、荧光标记、形状、精确选择；支持自由书写 | 拖动写画；直线 / 箭头 / 矩形另提供点起点、点终点；滚轮导航与工具操作避免争抢。 |
| TrackPoint | 定位、框注、箭头、修改、批注入口 | 支持点选完成形状与多边形选择，减少持续拖按；保留系统中键滚动，并提供手形工具等其他平移路径。 |
| Touchpad | 阅读导航、点选标记与修改；保留拖画 | 双指滚动 / 捏合遵循可用的系统映射；点选形状避免必须完成长拖动；抬指重定位不应被误当成连笔。 |
| Laptop 触屏 | 阅读、快速圈画、与鼠标 / 笔交替使用 | 无笔时提供明确的手指书写开关；用笔时优先笔写、手指导航；切换输入不重置工具与文档。 |
| Android 手机触屏 | 浏览、短标记、局部批注 | 提供书写 / 浏览切换、放大后批注、可直接触达的撤销；评估遮挡、系统边缘手势和键盘占用。 |
| Android 平板触屏 | 持续笔记、批注与较大范围编辑 | 验证手指书写、笔写、手掌接触、双指导航；分屏 / 旋转后命中和笔迹位置正确。 |
| 主动手写笔 | 连续书写、细致批注 | 读取真实压感与可用倾斜 / 按钮；验证取消、防误触、笔尖偏移和低延迟；无对应能力时正常降级。 |

TrackPoint / 触控板不以“长段自由手写是否和笔一样”作为唯一验收。建议比较完成同一批注任务的耗时、修正次数和主观疲劳；目前没有实测证明哪种策略更舒适。

文字批注框、贴便签可作为间接指针的重要补充候选：文字输入 / 排版 / 输入法由宿主负责，是否纳入首版对象类型待确认。文本高亮若依赖 PDF 文本范围，也必须由宿主提供语义，不能凭页面位图宣称已支持。

### 手势冲突与混合设备

- 用笔场景：建议笔负责写画，手指负责导航；手指书写由用户明确启用，不能要求设备一定有笔。
- 手指场景：浏览模式一指平移；书写模式一指写、双指导航。模式对用户可见，工具切换不能暗改模式。
- 从一指候选书写转为双指导航时，应撤掉尚未确认的候选笔迹，避免缩放后留下短线；具体提交时点另行验证，不先填写延时常数。
- 只在可辨识的活动笔接触 / 悬停等条件下启用相应防误触策略；不能因“曾用过笔”永久禁用手指。
- 每次操作确定输入所有者；明确处理抬起、取消、失焦与捕获丢失，取消中的笔迹不得变成完整笔迹。
- 活动笔划期间建议暂缓视口变换；若宿主必须改变视口，需先结束或取消当前操作。笔划之外保留正常导航。
- 不假定所有平台能区分鼠标、TrackPoint、触控板。识别不足时提供通用指针操作和用户偏好，保留系统指针速度与加速度。
- 不把中键、悬停、快捷键或多指手势作为唯一入口；关键编辑操作需要可点选的界面入口与键盘替代。

## 4 - 建议的模块边界

| 部分 | 职责 | 边界理由 |
| --- | --- | --- |
| 平台输入适配 | 接收原生样本、能力、时间、历史点、取消与指针捕获 | 原生数据不能先压成普通鼠标事件再尝试恢复压感。 |
| 输入意图与编辑逻辑 | 判断当前是写画、选取、擦除或导航；生成可撤销操作 | 宿主与模块须约定谁消费手势，防止一次动作同时滚页和画线。 |
| 可移植计算候选 | 曲线 / 几何、命中、编辑操作、文档恢复语义 | 不依赖账户、平台控件或窗口；是否共享代码仍待裁定。 |
| 显示适配 | 活动笔迹预览、已提交笔迹、局部更新、缩放裁剪 | 先比较原生手写与自绘路径，不因选 Rust 就强制统一 GPU 后端。 |
| 文档与宿主桥接 | 页面定位、变换与恢复、存储结果回报 | Scratchmark 管笔迹语义，宿主管真实存储和业务页面生命周期。 |

这只是职责划分，不代表要立即拆成五个包或五个线程。工具栏应能由宿主构建；引擎不固定某个应用的配色、文案和布局。

建议后续规格先回答：页面身份与修订、页面坐标单位、裁剪 / 旋转、屏幕到页面的变换、保存事务及失败恢复。笔迹应附着于稳定页面坐标，不保存为当前窗口像素；页面内容换版后不能默默套用旧批注。

例如：同一页从 100% 缩到 150%，下划线仍对应原句，是应验证的行为；只存一张叠加截图而无法选择和修改笔迹，不满足“重开后继续编辑”。可编辑数据是恢复依据，预览图 / 导出图单独处理。此处尚未指定数据字段和文件格式。

预测笔迹只用于显示、实际采样到达后替换；预测点不写入正式笔迹或撤销历史。平滑后的轨迹也需检查拐角与原意保持，不能仅凭视觉更圆润判定更好。

## 5 - 语言与复用方式

判断顺序建议是：两端输入与显示效果、宿主接入限制、长期维护成本，再考虑计算代码复用率。选择语言不能替代采样、线程调度与显示链路的测量。

| 候选 | 适合处 | 本项目的代价 / 采用条件 |
| --- | --- | --- |
| Rust 计算核心 + C# / Kotlin 原生适配 | 避免几何、命中、编辑与数据逻辑在不同应用间漂移；与现有 Rust 生态宿主接近 | 需要跨语言调用 FFI、双端打包和接口版本管理；UWP / .NET Native 尤须先验证；PezMax D5 是否允许外部共享库需裁定。当前优先研究。 |
| C# / Rust / Kotlin 各端实现，共享规格与夹具 | 与 PezMax 现行 D5 完全一致，可分别评估平台原生手写能力 | 算法与编辑功能需多份维护；视觉和数据语义的一致性必须有独立夹具证明。作为基线和备选。 |
| C++ 共享核心 + 原生适配 | 后续若发现必须复用的 C / C++ 引擎，可减少部分桥接 | 仍有跨语言调用、打包和手动内存管理成本；本轮没有必须选 C++ 的已核对依赖。保留条件候选。 |
| TypeScript / Web 画布 | 浏览器宿主或交互验证可能更直接 | 原生三端需要额外宿主接入；浏览器 API 存在不等于目标 WebView 能力或延迟达标。浏览器需求未确认，暂不列首选。 |
| C# 或 Kotlin 独占全部实现 | 单个平台路径直接 | 无法直接满足另一个已同等优先的平台及现有 Rust 宿主；不建议作为整个模块的唯一语言。 |

不建议为了复用模块而要求宿主迁移 UI 框架，也不因“以后跨平台”先引入统一应用外壳。当前没有新增依赖的授权或选定版本，本轮不安装框架。

如果采用平台原生手写处理或显示，需要先验证笔迹、笔刷属性和编辑结果能否转换并在另一端恢复；不应未经验证就把平台不透明存档作为跨端唯一数据依据。若转换会丢失语义，应缩小使用范围或调整方案，而不是仅凭原生预览更顺就确定采用。

若选择 Rust 候选，首个实验应是无 GPU 的最小计算 / 数据往返链路，加原生输入与显示对照；先证明宿主接得进去，再扩展算法。批量传递采样、明确内存所有权、阻止异常跨越边界是后续接口研究点，不在本文固化 ABI（语言间二进制调用约定）。

Rust 官方提供 C ABI 导出方式和相关平台目标，但这只支持“可以研究”的判断；它不证明 .NET Native、AppContainer、JNI、商店发布和全部架构已兼容。证据见核查记录 E5。

### PezMax-One 的既有裁定

`ARCHITECTURE.md` D5 明确“不共享实现”，不能自行解释成“外部 SDK 自动例外”。若保留 D5 且不允许例外，面向 PezMax 的建议就是平台实现加共同规格；若允许 Scratchmark 作为外部引擎复用，也只为手写能力明确例外，不改变各端业务与 UI 架构。

本轮不修改 PezMax 文档、不建立 submodule、不确定其集成方式。需要例外时，应在获得裁定后由后续接入任务更新该仓正典。

## 6 - 建议的最小范围与验证门

首轮建议保留：固定宽度笔、基础荧光标记、整笔擦除、撤销重做、平移缩放、点选直线 / 箭头 / 矩形、基础选择，以及可编辑保存 / 恢复。主动笔压力作为同阶段能力分支验证，不成为普通指针可用的前提。选择的具体方式需覆盖拖框和点选路径。

压力曲线调校、局部擦除、复杂套索、几何规整与高级笔刷随后评估。无限画布、OCR（文字识别）、手写识别、多人协作及 PDF 原生批注互转不放进这个最小闭环；这只是范围建议，不是长期否决。

| 验证门 | Windows 与 Android 的共同验收方向 | 当前状态 |
| --- | --- | --- |
| 宿主可接入 | 实际构建、安装、调用、回收资源；失败可报告；分别确认 .NET Native 与 Android 最低版本 / ABI | 未运行；共享核心方案需先裁定。 |
| 输入完整 | 起笔 / 快移 / 抬起 / 取消、历史样本、混合设备与导航不重复消费；有压感与无压感都能完成任务 | 未运行。 |
| 批注位置 | 页面缩放 / 旋转 / 裁剪、分屏、DPI 与重开后仍对应页面；内容换版有明确处理 | 未运行；坐标规格待确认。 |
| 数据可恢复 | 保存后重开可继续编辑；中断写入不损坏上一份有效数据；取消笔迹和预测点不被保存 | 未运行；跨会话是否保留撤销历史待讨论。 |
| 舒适度 | 各设备完成固定批注任务，记录耗时、修正 / 误触次数及疲劳评价；手机、平板分别评估 | 未运行；不能用模拟事件替代。 |
| 延迟与资源 | 分开记录输入到提交、呈现帧时间、端到端笔尖到显示延迟；报告 p50 / p95、丢帧、内存与功耗条件 | 未运行；软件日志不能替代真实端到端测量。 |

Windows 至少覆盖鼠标、TrackPoint、触控板、触屏笔记本及可用的主动笔；Android 至少覆盖手机手指、平板手指及可用的主动笔。不强制每台设备具备全部能力，也不要求先购买硬件。

Android 在目标设备支持时也需纳入外接鼠标 / 触控板与混合输入；不能将“移动端”直接等同于“只处理触摸”。首轮优先级不代表排除未来其他系统。

设备型号 / OS / 驱动 / 刷新率、页面尺寸与笔迹负载、任务脚本、测量方式和预算确认后，再约定量化门槛；不把未测的“低于多少 ms”写成已达标或已裁定要求。每个进入实现的实验先另交任务卡；付费、消耗配额或实机测试按工作台协定事先确认。

## 7 - 下一次讨论的裁定点

1. 复用方向：建议研究 Rust 计算核心与原生适配；PezMax 是否允许 Scratchmark 外部引擎例外，或继续严格执行 D5。
2. 后续手写板应用与 Ether 的关系，以及它需要固定页、无限画布还是两者；不阻塞本轮固定页分析。
3. 现有可用于验证的 Windows / Android 设备与主动笔能力；设备明确前不安排实机任务。

Windows 与 Android 同等优先已由用户确认，不再作为待选项。具体语言、显示后端、文件格式和对外契约仍待后续裁定。

## 8 - 纯引擎如何影响和验证手感

用户已确认纯引擎定位和上一轮推进方向，见裁定 D1 / D2。以下补充接口职责与验证方案，仍为设计建议，不定义正式 API。

### 实现的归属

“引擎抽象”指对宿主隐藏内部算法和平台细节，不表示引擎只提供空接口。建议由引擎实际处理平滑 / 压力映射、曲线与笔划几何、命中与编辑、文档状态；前端通过接口使用这些结果，并完成设备输入和像素呈现。

| 环节 | 建议由谁实现 | 影响的体验 |
| --- | --- | --- |
| 采集真实与历史样本、识别能力、指针捕获 / 取消 | 平台前端适配 | 样本是否完整、起笔与抬笔是否正确。 |
| 根据页面变换准备输入，分配书写与导航操作 | 前端与引擎约定一次所有权；前端执行平台导航 | 缩放错位、重复消费与误画。 |
| 从样本生成笔迹，完成命中、编辑与撤销 | 引擎 | 拐角是否保留、线宽变化、编辑结果。 |
| 根据引擎结果更新显示，安排重绘并提交帧 | 前端显示适配 | 显示延迟、掉帧与视觉反馈。 |
| 持久化读写、系统中断与页面生命周期 | 宿主执行 I/O，引擎处理可编辑状态 | 重开后能否继续编辑、错误能否恢复。 |

建议调用链：平台采样 → 前端整理输入 → 引擎更新笔迹 / 编辑状态 → 返回可显示的结果与变化通知 → 前端绘制并呈现。

不能只等抬笔后才输出完整结果；接口需要支持活动笔划的增量展示、结束确认与取消清除。前端应能区分正式笔迹和可替换的临时预览，避免预测轨迹被误存成文档内容。

### 展示输出的抽象

建议引擎提供与某个 UI 控件无关的展示结果。例如，引擎可计算曲线 / 轮廓及其笔刷样式，前端将结果提交给本平台绘图接口；也可另设可选渲染适配库，减轻不同宿主重复实现的工作。曲线、轮廓、三角网格或显示命令如何取舍，需后续实验，不在这里定案。

独立于 UI 不等于必须排除所有渲染计算：几何生成可以在引擎，窗口、绘图上下文和呈现时机在前端。若把平滑、压力映射、编辑等语义全部交给前端重写，复用同一引擎就难以约束结果。

展示结果应有清晰的更新与失效语义，避免前端必须每收一个点就重建全页。具体粒度、数据所有权与线程模型先在规格中确定，再实现绑定。

### 用参考前端展示手感

建议开发时为 Windows 与 Android 各准备一个最小参考前端：一张测试页面、基础工具、保存 / 重开入口、必要测量。它们是开发验证宿主，不是引擎依赖，也不是另立一个完整手写产品；当前均未实现。

参考前端通过未来对外提供的同一接口调用引擎，不使用绕过引擎的专用演示算法。原生手写路径可以作独立对照，但必须标明对照身份，不能把它的效果当作 Scratchmark 引擎的成果。

验证分开报告：引擎侧检查样本到笔迹 / 编辑结果和计算耗时；参考前端侧检查输入采集、绑定传递、活动笔迹更新和呈现；最终在明确设备上评价书写与批注舒适度。回放可以复现轨迹问题，不能替代实际设备采样和端到端体验。

参考前端验证通过，只能证明对应接入和设备条件。PezMax 或手写板应用仍需验证各自页面变换、事件处理和呈现链路，不能自动继承“手感已通过”的结论。
