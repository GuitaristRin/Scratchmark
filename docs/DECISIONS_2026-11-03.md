# 产品与架构方向裁定

状态：Canon。日期：2026-11-03。本文记录用户确认的方向，不定义接口签名、文件格式或具体依赖版本。

## D1 - 纯引擎定位

依据：用户明确“作为一个纯引擎”“具体实现需要前端调用接口来实现”。

Scratchmark 本体提供由前端调用的引擎能力，不拥有应用窗口、工具栏、平台事件循环或屏幕呈现。前端负责平台接入与展示；引擎仍需有笔迹计算、编辑和数据处理的具体实现，不能只剩接口声明。

手感属于引擎与前端接通后的整体体验。引擎计算验证与前端实际书写验证分别报告；不能用纯计算耗时或回放结果宣称实机手感已通过。

## D2 - 接受上一轮的复用与语言方向

依据：用户在上一轮推荐后表示“好的，我同意”，并进一步明确纯引擎边界。

按 Rust 计算核心、Windows C# / Android Kotlin 原生适配的方向继续设计；认可 Scratchmark 作为可被宿主复用的外部引擎这一方向。本轮不再将该方向重复列为待批准事项。

这是架构推进方向，不等于所有算法、显示后端、平台绑定方式和依赖已经确定，也不代表平台可接入性已经验证。Windows 与 Android 同等优先沿用 [PROJECT_BRIEF](PROJECT_BRIEF.md)。

PezMax-One 的既有正典尚未在该仓更新；未来实际接入前，需在已获同意的方向内完成外部引擎例外的文档衔接。本轮仍不修改该仓、不建立 submodule，不扩展为其他业务实现共享。

## 未裁定的细节

参考前端的具体结构、引擎的展示输出形式、接口与线程约束、手势分工、具体原生库和持久化格式仍属设计问题。上一轮提案未在本文件确认的细节，不因总体方向获同意而自动定稿。

## D3 - 开始工程实施与二进制分发验证

依据：用户在二进制分发与性能讨论后表示“可以，开始工程实施”。

按 [M0 实施任务卡](IMPLEMENTATION_M0.md) 开始首个有界工程闭环，先写实验规格再实现核心、C ABI 与独立宿主验证。二进制 SDK 可不依赖 submodule 接入；首阶段不将实验接口和快照格式宣称为稳定对外契约。

这不改变 Windows / Android 同等优先的产品要求；各目标的构建、运行和设备体验证据分别记录。未找到某目标工具链时，记录缺口，不以另一平台结果代替。

## D4 - 继续 M1 宿主适配验证（2026-11-04）

依据：用户审阅 [M1 实施任务卡](IMPLEMENTATION_M1.md) 后明确选择“按任务卡继续”。

按该卡推进 Windows C# 无 UI 实际调用闭环，同时核查 Android 接入工具链。缺少工具链时记录缺口，不安装大型组件、不操作真机、不改 M0 ABI。此授权不构成正式托管 API 或长期快照格式承诺。

## D5 - 暂缓 Android、回到主功能（2026-11-04）

依据：用户明确“android之后再考虑好了，继续实现主功能”，并表示自己负责开始 PezMax-One 的初步重构。

暂缓 Android 接入与组件安装，撤回待答复的组件补齐请求，研发重心回到引擎主功能。这是当前实施顺序调整，不改变产品长期平台范围。PezMax-One 由用户推进，本 agent 继续只修改 Scratchmark，不建立 submodule。

## D6 - 优先平滑与压力笔刷（2026-11-04）

依据：用户在阶段选择中明确“先做平滑与压力笔刷”。

按 [M2 任务卡](IMPLEMENTATION_M2.md) 推进原始样本之外的在线平滑轨迹和逐点笔宽，贯通核心与 SDK；擦除、删除后续再推进。读取配置由宿主保留，快照仍保存原始样本，不把本轮派生几何说成每笔笔刷样式已持久化或设备手感已达标。

## D7 - 部署用户提供的 NDK（2026-11-04）

依据：用户提供下载目录中的 android-ndk-r30 路径并要求“部署一下先”。

将该已有 NDK 复制到现有 SDK 的标准 side-by-side 目录并验证，保留源目录。本次只准备 NDK，不下载 Rust Android 目标、不启动模拟器或操作设备，继续以 M2 主功能为当前研发重点。

## D8 - 局部擦除作为下一步引擎主功能（2026-11-05）

依据：用户要求“继续推进引擎主内容推进”，并在 M5 范围选择中明确“局部擦除：沿擦除路径切分笔划”。

按 [M5 任务卡](IMPLEMENTATION_M5.md) 推进沿擦除路径的切分，先写 `spec/M5.md` 再改实现；M4 的命中与整笔擦除保持不变。这是功能顺序的指定，不接受本轮把切分结果说成设备手感或擦除性能已达标，也不改变 Android 暂缓与不修改 PezMax-One 的边界。

套索、形状工具、选区移动、预测笔迹与多页管理仍待后续选择，不在本裁定内。

## D9 - 按便签验证器暴露的差距继续补齐（2026-11-06）

依据：用户表示“可行，你开一个目标开始继续做 fill 工作，持续推进即可，目前研究结论和参考库充足”。

持续目标：按 [REFERENCE_FINDINGS](REFERENCE_FINDINGS.md) 的已核对能力与 `Projects/Scratchmark-Verifier` 的对照清单，逐轮补齐引擎能力，每轮先写 spec 与任务卡、再实现并验收。顺序为选择与批量删除（含清空）→ 选区变换 → 形状规整 → 视口旋转 → 预测笔迹。

这是授权持续推进，不是把未实现项当作已完成；每轮的证据等级与未验证项仍按 STATE 分开记录，构造不出设备证据的部分继续标为未验证。`.paint` 文件兼容属于未解析的私有格式，不在该序列内。

## D10 - M6 范围：套索命中、批量删除与清空（2026-11-06）

依据：D9 的执行顺序第一项，同时关闭验证器实测到的两个缺口。

按 [M6 任务卡](IMPLEMENTATION_M6.md) 与 `spec/M6.md` 推进：引擎只提供只读命中查询与按索引的原子删除，不保存选区状态，不做选区变换。撤销粒度按“一次调用一个条目”，清空不再由宿主逐笔删除。

## D11 - M7 范围：选区变换与复制粘贴（2026-11-06）

依据：D9 执行顺序第二项，M6 之后框选已可用但缺少“选中后改一改”的闭环。

按 [M7 任务卡](IMPLEMENTATION_M7.md) 与 `spec/M7.md` 推进：仿射矩阵表达平移 / 缩放 / 旋转 / 镜像 / 剪切，剪贴板内容是格式 1 快照字节而不是引擎内状态，系统剪贴板集成与变换手柄留在宿主。
变换与粘贴各自只占一个撤销条目，任何越界都整次失败，不做部分生效。
## D12 - M8 范围：形状规整（2026-11-07）

依据：D9 执行顺序第三项，主流移动便签侧已有形状与形状规整接口，Scratchmark 尚无。

按 [M8 任务卡](IMPLEMENTATION_M8.md) 与 `spec/M8.md` 推进：种类由宿主显式指定，引擎不做自动分类；先支持质心主方向直线、轴对齐矩形、Kåsa 圆与箭头三种几何的规整，并给预览模式让宿主按自己的残差阈值决定是否采纳。
规整只生成普通笔划（继承颜色与线宽），不引入新的编辑类型，快照格式保持 1 / 2。
